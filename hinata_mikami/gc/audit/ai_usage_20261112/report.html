③ 方針転換と誤りの具体例

A. 所有権取得で停止した関数にtrust_meを提案した（直接のAI発言あり）

6月2日の「RefinedRust 検証エラー」では、read_next_valueの型付け停止に対し「trust_meが付いていない」ことを原因と説明し、付加を提案した。さらに証明モジュールを除くためoutputディレクトリを削除・再生成する手順も案内していた。原発言の抜粋。

trust_meは契約を仮定して本体の証明を要求しないモードであり、所有権を取り出す証明は完成しない。is_assumed / needs_proof。一時的な切り分け目的なら利用し得るが、本体の検証完成を求める局面の解決策にはならない。この抜粋に至る全対話は取得できていないため、それ以前の切り分け方針の有無は留保する。永続手動証明を含む出力全体の削除も、研究記録を失う危険のある提案だった。現在のGCにtrust_meはない。

B. 正しい定義を誤読して変更対象と判断した（直接の訂正発言あり）

10月13日の「sweep検証条件と実装方針」では、ユーザーが元のsweep_nodes_invを再提示すると、AIは「最初から正しい定義」「読み違い」「invariantを変更する必要はありません」と訂正した。会話の抜粋。この局面の差は、length marks と Z.to_nat(length locs)、および簡約されたリスト式の表現をそろえることだった。正規化・型合わせの停止を、不変条件設計そのものの欠陥と取り違えかけた例として使える。

C. sweep中の一時的なnext不整合から、余分な実装処理へ進んだ

9月15日の原メモは、dead A → dead BでBを先に削除するとHnext_validが崩れることと、deadノードのnextをNULLにする→削除→mark解除の3段階案を記録している。同じメモに、常時の成立を求める必要への疑問と実行時オーバーヘッドへの懸念がある。9月15日の原資料本文。9月14日のAI提案だったことは過去会話検索の要約にも残るが、当該提案の会話全文は未取得。

現行は #rawによる境界仕様 と 中間状態用のループ不変条件 を用い、後方からの単一ループ で証明されている。従って、このNULL化処理が今回の検証に必須という判断は支持されない。一時的な不整合があるという観察自体は正しい。

ただし、現行の成功は#rawによって仕様の与え方を変えた結果である。元の通常のHeap不変条件付きメソッドのまま無変更で証明できたとは主張しない。実行時間の比較実験も今回確認していない。

D. Node側への注釈付与を不可能と一般化する根拠はない

Heapが全ノードを一度ずつ所有し、nextを非所有ポインタとして扱う構成は、循環する参照関係と所有権を分離するために自然である。一方、「Nodeにどのような不変条件も付けられない」は別の強い主張になる。現在の実装・メモ・前段のCellの畳み直し失敗から、その不可能性は導けない。Nodeに局所的な性質だけを置く設計まで否定する証拠はない。

発表では「Heapに所有権とノード間整合性を集約する設計を採用し、その構成で検証した」と述べる。現在の Node直前のコメント は経験メモとして扱い、一般的な不可能性の根拠にはしない。

E. 実際に偽だった旧補題が2件ある（誤りは確認、初出作成者は未確定）

以下は 10月19日の反例と修正記録、644763f1の旧宣言、現行ソースを照合した。AI支援中の証明課題設計の失敗として有用だが、全対話がそろわず、旧宣言を最初に書いた主体がAIだったことは断定しない。Codexが反例を提示し修正・完成したことは編集記録で直接確認できる。

旧補題誤り・反例修正
sweep_nodes_inv_step任意の添字依存Φを削除後にも保存するとした。Φ(k,v)=「v=k」、vals=[0,1]、marks=[false,true]、cut=1では、先頭削除後に値1の添字が0になりΦが崩れる。ノードの所有権述語Φから不要な添字を除いた。リスト上の位置対応はaligned_nodesが扱う。
marks_closed_keep_marked_next_valid元のnextの有効性が前提になかった。locs=[a], nexts=[b], marks=[true]、bが非NULLかつ未登録でもmarks_closedは成立し得るが、残存nextは有効でない。元のnext有効性と管理アドレスの非NULL性を明示。現在の 修正版の前提。

この2件では、タクティクを強化し続けても旧命題は証明できない。反例を作って命題の一般化のしすぎ・前提不足を検査する必要があった。

F. 解放イベントの回数証明を必須のように扱った説明も訂正された

10月23日のユーザーの問い直しに対して、AI自身が、以前の「解放イベントの回数までの証明」を今回の目的に必須のように扱うべきではなかったと訂正している。訂正の記録。Box / allocator のonly_specに依存すること、Rust関数の契約を証明すること、独自に実行履歴・Freeイベントを証明することの範囲を混同して追加課題を膨らませる危険があった。

この訂正により、実際の物理解放やcollectの未検証という境界がなくなるわけではない。現在の Drop検査の説明 は、静的CFG検査と全実行履歴の証明を区別している。

アノテーション・抽象化の過不足

論点精査結果
Rocq上のmarkモデルだけでmarked ↔ reachableを示す案数学モデルの性質を示すことは有効な証明分割。ただしRust本体がそのモデルに従うことを別途示す必要がある。現在はmark_fromのensuresでmark_from_relを保証し、純粋なexact_root補題をmarkの証明へ適用している。数学部分を分離したこと全般を誤りと説明しない。「純粋なmark関数だけで済ませようとした」という旧具体案の全文は未取得で、関数名・試行回数は確定できない。
NoDup locsの不足純粋な添字モデルでは同じアドレスに複数の添字が付くと、mark遷移が1つだけを選ぶのにreachableは両方について証明できる。例：locs=[A,B,B]、nexts=[B,NULL,NULL]。NoDupを補って完全性を示し、allocにも新規性の証明を追加した。これはRustプログラムの欠陥という判断ではない。
marks_closedだけで残る ↔ reachableを無条件に要求過剰な要求。marks_closedは非到達ノードへの過剰マークを許す。非到達BもtrueならBが残る。現行sweep_postはmarking_exactを仮定する条件付きの結論。markの結果との論理的合成は別定理で示されている。
元のmarksと実markedビット開始時スナップショットを保持判定に使う。実markedはfalseに戻るため、ビットそのものの不変を要求すると実装と矛盾する。未処理prefixの保存と、終了時のリセットを分ける。
observe / 実メモリの所有権条件必要。開始時リストから計算した数学的な期待値だけでは、実際の終了後のVec・Nodeフィールドに結び付かない。observeがVec更新、#iris条件が実メモリのvalue/next保存・mark解除と所有権を担う。
10月23日に追加したensuresの重複sweep_fields_preservedとall_unmarked(replicate ... false)は、元の所有権条件と補助定理から導けた。10月26日に該当2ブロックを削除し、整合性5条件を連言にまとめ、事後条件ブロックを10個から4個に整理。単に削除した個数を「保証が6つ不要だった」と解釈しない。
固定2ノードの例最小例としては妥当。ただしそのrequires/argsのまま任意長のGCを検証したとは言えない。実際にユーザーが対象の狭さを指摘し、AIが固定2ノード用と認めた会話がある。
read_next_valueの強い所有権前提現在の補助関数はnodeとnext双方の排他的所有権を別々に要求する。node=nextの自己参照へそのまま適用すると資源が重複するため、このヘルパーの契約は自己参照の読み取りを含む一般APIとしては狭い。現行mark_fromはこのヘルパーを呼ばず、自身で所有権を取り出すので、GCの自己参照対応を否定するものではない。この指摘は現行仕様の読み取りに基づくもので、自己参照用の新規証明は実行していない。
mark_fromに残る_dummy不変条件の自動開示を促すためのVecアクセスが現在も実コードにある。証明のために実装へ補助アクセスが入った例として挙げられる。ただし最適化後の実行時コストは測定しておらず、手動証明で取り除けるかも今回検証していない。

関連ソース：mark_fromの契約と実装、markの到達可能性仕様、exact_root、本証明での補題適用、仕様整理の記録、read_next_valueの前提。

発表に使えるメッセージ

生成AIは、定義・補題の具体化や証明スクリプトの補完に役立った。一方、証明自動化が停止する原因を、不変条件や実装の制約と取り違え、追加の実装処理や検証の回避を提案する場面があった。Rocqによる検査に加えて、仕様の十分性、前提の強さ、Rust実装と数学モデルの対応を研究者が確認した。

発表の具体例には、直接のAI発言が残るtrust_me提案と定義の読み違いを使いやすい。sweepのNULL化案は「必要性の根拠が弱かった」という評価にし、偽だった2補題は「AI支援中の課題設計の点検」として初出帰属を留保する。純粋Rocqへの分解は、有効な部分と実装との接続が必要な部分を両方説明する。

検証状況と本調査の限界

本調査ではソース・Git履歴・実際のCodex編集入力・取得できた過去チャット・Google Docs本文を照合した。生成やRocqビルドを新たに実行していない。現在の永続証明12ファイルすべてが10月26日の監査記録のSHA256と一致することを確認した。補助gc_defs.vの11月4日差分はコメント5行のみで、ほかの補助ライブラリ・Drop検査ソースも監査時のハッシュと一致する。既存の10月26日のビルド・79件の依存監査記録は 監査報告 にある。79は今回のProofブロック全92件の全数ではなく、その監査で列挙した対象数である。

AI帰属には、直接の編集証拠、直近のチャット原発言、当時の研究者メモ、過去検索の返却要約という強さの違いがある。古い全対話・AIが提案した全案・すべての採否・人間のみの比較実験はそろっていない。件数割合から、AIが研究全体の何割を遂行したか、何倍速くしたか、完全自動で成功した率を導かない。

RefinedRustの証明自動化と生成AIも分ける。RefinedRustの生成証明をRocq/Coqが検査する構成は 原論文 の説明に対応する。検査された命題が研究目的を十分に表すか、未検証の契約をどこまで仮定するかは別途確認が必要である。
